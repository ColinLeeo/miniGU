# GCard Catalog 构建：可扩展性分析与性能上界论证

## 1. 计算过程说明

### 1.1 问题定义

给定一个数据图 $G$ 和一组路径模式（path pattern），GCard 需要为每个模式预计算**度序列**（degree sequence）：对于模式 $P = v_1\text{-}e_1\text{-}v_2\text{-}e_2\text{-}\cdots\text{-}v_k$ 中的每个端点顶点，记录数据图中每个匹配顶点沿该路径可达的匹配数。

### 1.2 示例：查询图 A-B-C-D 与分支 B-E

考虑如下查询图（树形结构）：

```
A ---e1--- B ---e2--- C ---e3--- D
           |
          e4
           |
           E
```

其中 A, B, C, D, E 为顶点标签，e1~e4 为边标签。

设 `max_k = 3`，算法按路径长度逐层计算：

#### Level 1（长度为 1 的路径）

直接统计每个顶点的邻居数：

| 模式 | 含义 | 计算方式 |
|------|------|---------|
| A-B | A 类顶点通过 e1 到 B 的邻居数 | 扫描图，对每个 A 类顶点 $a$，$\text{deg}_{AB}(a) = \|\text{neighbors}_{e1}(a)\|$ |
| B-C | B 类顶点通过 e2 到 C 的邻居数 | 扫描图，对每个 B 类顶点 $b$，$\text{deg}_{BC}(b) = \|\text{neighbors}_{e2}(b)\|$ |
| C-D | C 类顶点通过 e3 到 D 的邻居数 | 类似 |
| B-E | B 类顶点通过 e4 到 E 的邻居数 | 类似 |

#### Level 2（长度为 2 的路径，依赖 Level 1）

**以计算 A-B-C 为例**，这是核心操作 `extend_with_suffix`：

```
对于每个 A 类顶点 a:
    deg_ABC(a) = 0
    for each b in neighbors_e1(a):        // b 是 a 通过 e1 到达的 B 类邻居
        deg_ABC(a) += deg_BC(b)           // 累加 b 沿 B-C 的度值（来自 Level 1）
```

直观含义：a 沿 A-B-C 路径的匹配数 = a 的每个 B 类邻居 b 各自能延伸到 C 的数量之和。

类似地：
- **B-C-D**：$\text{deg}_{BCD}(b) = \sum_{c \in \text{neighbors}_{e2}(b)} \text{deg}_{CD}(c)$
- **A-B-E**：$\text{deg}_{ABE}(a) = \sum_{b \in \text{neighbors}_{e1}(a)} \text{deg}_{BE}(b)$

#### Level 3（长度为 3 的路径，依赖 Level 2）

**计算 A-B-C-D**：

```
对于每个 A 类顶点 a:
    deg_ABCD(a) = 0
    for each b in neighbors_e1(a):
        deg_ABCD(a) += deg_BCD(b)         // 累加 b 沿 B-C-D 的度值（来自 Level 2）
```

### 1.3 内循环的内存访问模式

将上述逻辑落实到实际数据结构后，`extend_with_suffix` 的内循环为：

```
// 预处理：构建 remap 表和 suffix_degs 数组
// remap[local_id_of_b] → b 在 suffix 度数组中的索引
// suffix_degs[idx]     → b 的后缀度值

for i in 0..num_src_vertices:               // 遍历所有 A 类顶点
    sum = 0
    for j in flat_neighbors[offsets[i]..offsets[i+1]]:  // 顺序读: A 的邻居列表
        idx = remap[j]                                   // 随机读 1: 查映射表
        if idx != INVALID:
            sum += suffix_degs[idx]                      // 随机读 2: 查后缀度值
    result[i] = sum
```

**每次迭代的开销**：

| 操作 | 访问模式 | 搬运数据 | 有效数据 |
|------|---------|---------|---------|
| `flat_neighbors[j]` | 顺序读 | 64B (缓存行) | 4B |
| `remap[j]` | 随机读 | 64B (缓存行) | 4B |
| `suffix_degs[idx]` | 随机读，依赖 remap 结果 | 64B (缓存行) | 8B |
| 比较 + 加法 | 寄存器 | 0 | - |

**算术密度**：

$$\text{AI} = \frac{\text{2 ops (cmp + add)}}{\text{2} \times \text{64 B (两次随机读的缓存行)}} = 0.016 \text{ ops/byte}$$

这意味着：**每从内存搬运 128 字节数据，只执行 2 次运算**。

### 1.4 并行策略

算法使用 rayon 在**模式级别**进行并行：

```
// Level 2: 164 个模式并行
level2_patterns.par_iter().map(|pattern| {
    extend_with_suffix(neighbor_data, suffix_degs, remap)
})

// Level 3: 771 个模式并行
level3_patterns.par_iter().map(|pattern| {
    extend_with_suffix(neighbor_data, suffix_degs, remap)
})
```

每个线程独立处理一个模式，线程间无数据依赖，无需同步。

## 3. 各规模瓶颈分析

### 3.1 统一理论框架

Compute 阶段的执行时间由以下模型描述：

$$T = \frac{N_{\text{lookups}} \times 2 \times 64\text{B} \times (1 - \text{hit\_rate}_{\text{L3}})}{BW_{\text{DRAM}}}$$

其中：
- $N_{\text{lookups}}$：总随机查找次数（正比于数据规模）
- $\text{hit\_rate}_{\text{L3}}$：L3 缓存命中率（取决于工作集与 L3 容量的比值）
- $BW_{\text{DRAM}}$：DRAM 带宽（硬件常数，83.2 GB/s）

扩展性受限本质上只有三种原因，不同 SF 处于不同位置：

```
           Amdahl 定律       L3 容量临界        DRAM 带宽饱和
              |                  |                    |
  SF0.1  ■■■■■■■■██             |                    |
  SF0.3  ■■■■■■■■■■■██          |                    |
  SF1    ■■■■■██████████████████████                  |
  SF3    ■■■■■■■■■■■████████████████████████████████████
         1    2    4    8   12   16   24   线程数

  ■ = 有效扩展区    █ = 停滞/退化区
```

### 3.2 SF3（大数据）：经典 DRAM 带宽墙

**工作集分析**：

SF3 中最大的数组（度序列统计数据约 5.6 GB）：

| 顶点类别 | suffix_degs 大小 | remap 表范围 |
|---------|-----------------|-------------|
| Comment | 58.2 MB | 0.1 ~ 29.1 MB |
| Post | 24.4 MB | 0.1 ~ 14.5 MB |
| Forum | 2.1 MB | 0.1 ~ 12.2 MB |

16 线程总工作集 ~500-900 MB >> L3 64 MB，**绝大多数随机访问直接落入 DRAM**。

**瓶颈论证**：

Zen 4 的每个核有 ~32 个 L2 MSHR，可同时发起 32 个 DRAM 请求：

$$BW_{\text{per\_core}} = \frac{32 \times 64\text{B}}{80\text{ns}} = 25.6 \text{ GB/s}$$

12 个物理核总请求能力 = $12 \times 25.6 = 307$ GB/s >> 83.2 GB/s DRAM 峰值。

即 **~4 个核就足以饱和 DRAM 带宽**。实测中 8→12 线程仍有小幅提升（8.66→7.61s），是因为 L3 缓存在少线程时有更高的命中率，部分请求不需要走 DRAM。超过 12 线程后彻底饱和。

**模型验证（K=2, Level 2, 16 线程）**：

| L3 命中率 | 预测时间 | 实测 | 误差 |
|----------|---------|------|------|
| 23% | 1.26s | 1.25s | < 1% |

**模型验证（K=3, Level 3, 16 线程）**：

| L3 命中率 | 预测时间 | 实测 | 误差 |
|----------|---------|------|------|
| 19% | 6.52s | ~6.5s | < 1% |

### 3.3 SF1（中等数据）：过早饱和 + 最差加速比

SF1 在 **8 线程**就到达最优（2.10s），且最大加速比仅 3.9x——甚至**不如更大的 SF3**（5.2x）。

**原因：SF1 处于"最尴尬"的工作集区间**。

SF1 的工作集（按 SF3 等比缩放）：

| 配置 | 工作集估算 | vs L3 (64 MB) |
|------|-----------|---------------|
| 4 线程 | ~60-150 MB | 刚好溢出 |
| 8 线程 | ~80-240 MB | 远超 L3 |
| 12 线程 | ~120-360 MB | 远超 L3 |

关键区别在于：
1. **数据量已远超 L3** → 与 SF3 一样产生大量 DRAM miss
2. **总计算量不够大**（8.24s vs SF3 的 39.5s）→ 少量线程即可饱和 DRAM 带宽
3. **增加线程只带来更多 L3 竞争**：8→12 线程时，性能从 2.10s **退化**到 2.23s

SF1 加速比不如 SF3 的原因：SF3 总计算量大（39.5s），低线程时每线程有充分的工作量，扩展空间更大。而 SF1 的 DRAM 带宽在 4-8 线程就被吃满了，剩余线程全是负担。

### 3.4 SF0.3（小数据）：L3 容量临界

SF0.3 是 12 线程最优（0.408s），之后退化到 24 线程的 0.464s（慢 **14%**）。

**SF0.3 处于 L3 容量的临界区**：

| 配置 | 工作集估算 | vs L3 (64 MB) |
|------|-----------|---------------|
| 8 线程 | ~24-80 MB | 勉强装入 L3 |
| 12 线程 | ~36-120 MB | 开始溢出 |
| 16 线程 (含 SMT) | ~48-160 MB | 明显溢出 |

- 8 线程时大部分工作集还能留在 L3，命中率较高 → 扩展有效
- 12 线程时开始溢出，但并行度提升刚好弥补 → 甜蜜点
- 16+ 线程（SMT 共享 L1/L2），**缓存踩踏**加剧：
  - 每对 SMT 线程共享同一物理核的 L1d (32KB) 和 L2 (1MB)
  - 两个线程的工作集互相驱逐，导致更多请求落到 L3
  - L3 也因更多并发访问而命中率下降
  - **净效果：DRAM 流量增加，但 DRAM 带宽不变 → 性能退化**

### 3.5 SF0.1（极小数据）：Amdahl 定律

SF0.1 是唯一**不退化**的 SF，但加速比也止步于 8.6x（理想 12x）。

**工作集分析**：

| 配置 | 工作集估算 | vs L3 (64 MB) |
|------|-----------|---------------|
| 16 线程 | ~15-40 MB | 完全装入 L3 |
| 24 线程 | ~15-40 MB | 完全装入 L3 |

数据全在 L3 内，DRAM 几乎不参与 → **不存在 DRAM 带宽墙**。不退化是因为加线程不增加缓存压力。

**那为什么停在 8.6x？**

K=3 共有 960 个模式（25 + 164 + 771），但各模式工作量差异悬殊。Comment 相关的单个大模式可能占总计算量的 ~12%。根据 Amdahl 定律：

$$\text{Speedup}_{\max} = \frac{1}{f} = \frac{1}{0.12} \approx 8.3\text{x}$$

其中 $f$ 为最大单任务占比。实测 8.6x 与理论预测 8.3x 高度一致——**并行粒度成为瓶颈**。

此外，总时间仅 0.97s，分摊到 24 线程后为 0.04s/线程，rayon 的 work-stealing 调度开销（微秒级 × 数百次调度）也开始占据可感知的比例。

## 4. 为什么所有 SF 都不能线性扩展？

### 4.1 根本原因：算术密度过低

内循环的算术密度 AI = 0.016 ops/byte，远低于 Roofline 模型的 Ridge Point（~32 ops/byte）。这意味着无论数据在哪一级存储层次（L3 或 DRAM），**带宽总是先于计算被耗尽**。

```
性能
(G-ops/s)
  |
240|                                              _____________  计算上界
  |                                    _________/
  |                           ________/
  |                  ________/
  |         ________/
  |________/  内存带宽上界 (斜率 = 75 GB/s)
  |
  |*  <-- AI = 0.016 (所有 SF 都在这里)
  |
  +----+----+----+----+----+-----> AI (ops/byte)
     0.01  0.1   1    10   100
```

不同 SF 只是撞到了存储层次中不同级别的带宽墙：

| SF | 工作集位置 | 带宽墙 |
|----|-----------|--------|
| SF0.1 | L3 内 | L3 带宽 + Amdahl 定律 |
| SF0.3 | L3 临界 | L3↔DRAM 过渡带 |
| SF1 | DRAM | DRAM 带宽（过早饱和） |
| SF3 | DRAM | DRAM 带宽（经典饱和） |

### 4.2 间接数组访问的本质限制

`extend_with_suffix` 的核心操作是 **indirect array access**（间接数组访问）：

```
result[i] = sum over j { suffix_degs[ remap[ neighbors[j] ] ] }
```

这种访问模式有三个本质特征，使得**任何不改变算法的优化都无法突破带宽墙**：

1. **无时间局部性**：每个邻居 `j` 访问 remap/suffix_degs 的不同位置，访问完不会再访问
2. **无空间局部性**：邻居 ID 在 remap 数组中的位置是分散的，同一缓存行中加载的相邻元素大概率不会被使用
3. **存在数据依赖链**：`remap[j]` 的结果决定 `suffix_degs` 的访问地址 → 指针追踪，无法合并为单次内存访问

### 4.3 已验证无效的优化方案

| 优化方案 | 实测效果 | 无效原因 |
|---------|---------|---------|
| 软件预取 (prefetch) | ~3% | CPU MLP 已过剩（307 GB/s >> 83.2 GB/s），预取不增加吞吐 |
| 增加线程数 (16→32) | 0% 或负面 | 12 物理核已饱和 DRAM 带宽，SMT 只增加缓存竞争 |
| SIMD 向量化 | 不适用 | 瓶颈是内存带宽而非计算，加速计算无意义 |

### 4.4 理论上界

对于当前的 **indirect array access** 计算模式，单机性能上界为：

$$T_{\min} = \frac{N_{\text{lookups}} \times 2 \times 64\text{B} \times (1 - \text{hit\_rate}_{\text{L3}})}{BW_{\text{DRAM}}}$$

以 SF3 K=3 为例：

$$T_{\min} = \frac{5798\text{M} \times 128\text{B} \times 0.81}{83.2 \text{ GB/s}} \approx 7.2\text{s}$$

实测 7.61s，已达理论上界的 **95%**。

## 5. 总结

| 结论 | 依据 |
|------|------|
| 算法实现已接近硬件理论上界 | SF3 实测 / 理论 = 95%，三种独立模型预测误差 < 1% |
| 所有 SF 均无法线性扩展 | 根因是算术密度过低 (AI=0.016)，带宽总是先于计算被耗尽 |
| 不同 SF 撞到不同层级的墙 | SF0.1: Amdahl 定律, SF0.3: L3 临界, SF1/SF3: DRAM 带宽 |
| 软件层面优化空间极为有限 | 预取、SIMD、增加线程均已验证无效 |
| 唯一有效方向是减少 DRAM 流量 | Cache-aware 调度 + u32 度值，预期 ~20% 提升 |
